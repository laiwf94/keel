# Benchmark results

## Compaction pause and catch-up for 1, 4 and 16 GiB logs

`./gradlew logBenchmark` runs `bench/LogBench.java` (`io.github.laiwf94.keel.bench.LogBench`) in a JVM with a 256 MiB heap. `-Psizes=1g,4g,16g` picks the sizes, and `-Pdir=/path` picks the directory the data goes in. The largest size needs about twice its size in free disk. Both cases use `FileStorage` in a real directory. Nothing is mocked except the network.

- **Compaction.** The benchmark writes a log of the given size: entries of 1 KiB, synced every 1 MiB, in the default 64 MiB segments. It then installs a snapshot 1,024 entries before the end. The pause is the time `FileStorage.saveSnapshot` blocks the node's thread: a directory fsync after the snapshot file's rename, then one unlink and one directory fsync for each segment the snapshot covers. The state machine's own snapshot is left out of this case, because its cost depends on the size of the state, not of the log. The catch-up case measures it.
- **Catch-up.** A single-node leader has a state of the given size. This is `FillerMachine`, whose snapshot is generated bytes that the restore checks one by one. The leader snapshots that state, then appends 1,000 entries of 1 KiB, and then adds a new server. The clock runs from the configuration change until the new server is a voter and has applied everything the leader has. Every message goes through the wire codec and is passed in memory, so the network itself is not measured.
  - *snapshot ms*: the leader's longest round on its node thread, the one that serializes the state into the snapshot file and installs it.
  - *transfer*: the chunked InstallSnapshot, from the configuration change until the new server has fsynced and installed the file.
  - *restore*: the new server reading and checking its file.
  - *tail*: the entries after the snapshot and the promotion to voter.
- **heap MiB** is the most heap in use right after any garbage collection during the case. That is an upper bound on the live data a smaller heap would have to hold.

### 2026-11-28, Linux x86_64, 4 vCPUs, 15 GiB RAM

The machine is a 4-vCPU Xeon VM at 2.10 GHz with 15 GiB of RAM, on kernel 6.18. The disk is a virtio block device with ext4 mounted with `discard`. The JDK is OpenJDK 21.0.13 with G1 and `-Xmx256m`. The code is commit 23f8d82 plus the benchmark itself.

```
compaction
log         entries  segments write MB/s   deleted  pause ms   fsyncs rewrites   heap MiB
1 GiB       1048576        17        265        16     509.3       17        0        6.5
4 GiB       4194304        66        266        65    2222.3       66        0       23.5
16 GiB     16777216       264        240       263    9288.7      264        0      100.3

catch-up (snapshot chunks of 1 MiB, 1000 entries of 1024 bytes after the snapshot)
state     snapshot ms  transfer s transfer MB/s  restore s  tail ms   total s   chunks   wire MiB  match   heap MiB
1 GiB            1447        2.85          359       0.56     15.6      3.42     1025       1025    yes       50.9
4 GiB            4368        8.78          466       1.96     17.5     10.76     4097       4098    yes       86.2
16 GiB          15266       43.59          376      13.67     13.1     57.28    16385      16387    yes       70.3
```

What the numbers say:

- **Compaction rewrites nothing, but its pause still grows with the log.** No run rewrote the log. The pause is 32 to 35 ms for each segment deleted: 0.5 s for 1 GiB, 2.2 s for 4 GiB and 9.3 s for 16 GiB.
  - Almost all of that time is the unlink. On this volume, unlinking a 64 MiB file takes about 30 ms, and the directory fsync after it takes 0.3 ms. A Python loop that does only those two calls gives the same split.
  - With the default election timeout of 10 ticks of 25 ms, each of these pauses is long enough for followers to start an election.
  - So the segmented log removed the rewrite, but not the pause. Deleting covered segments has to move off the node's thread. That is the next task in #25.
- **The leader's own snapshot is the larger pause.** Serializing the state into the snapshot file blocks the node thread for about 0.95 s per GiB: 1.4 s, 4.4 s and 15.3 s. `KvMachine` snapshots on the same thread, so a large in-memory data set pauses its leader the same way. Week 9 replaces it with a disk-backed state machine whose snapshots come from its data files.
- **Catch-up is bounded by disk speed, not by memory.**
  - A new server catches up at 360 to 470 MB/s of snapshot: 3.4 s for 1 GiB, 10.8 s for 4 GiB and 57 s for 16 GiB.
  - The JVM holds both nodes, and its live heap never went above 90 MiB. The heap is capped at 256 MiB.
  - The 16 GiB restore runs at 1.2 GB/s, against 1.8 to 2.0 GB/s for the smaller ones. Its file does not fit in this machine's 15 GiB page cache, so it is read back from disk.
- **The log's in-memory index is 4 bytes per entry.** The live heap of the compaction case grows with the number of entries: 100 MiB for 16 million entries of 1 KiB. A log of 100-byte entries would need about ten times as much heap per GiB.
- **No chunk was resent.** Each chunk count is the snapshot file's size in MiB, rounded up. The file is the state plus its head, metadata and trailer. Message headers add under 0.05% on the wire.
